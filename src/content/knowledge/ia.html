IA

Desarrollo con IA

Guia practica para trabajar con IA sin perder el control: pedir bien, dar contexto, documentar decisiones, implementar con agentes y verificar antes de aceptar cambios.

1 Pedir

Define rol, contexto, tarea, restricciones y formato.

2 Contextualizar

Usa AGENTS.md, specs, docs, MCP y skills para reducir ambiguedad.

3 Ejecutar

Trabaja con agentes, Build/Plan mode y tareas pequenas.

4 Verificar

Lee el codigo, ejecuta tests, revisa riesgos y ajusta el bucle.

1. Prompts y seguridad

Idea clave: un buen resultado empieza por una instruccion con arquitectura. Si el prompt es ambiguo, el agente rellena huecos inventando decisiones.
Evita: pedir "hazme X" sin stack, restricciones, criterios de aceptacion ni formato de salida.

Plantilla de prompt perfecto

[1. Rol]
Actua como [perfil experto] especializado en [area].

[2. Contexto]
Estoy construyendo [producto/proyecto] usando [stack/versiones]. El objetivo es [objetivo].

[3. Tarea]
Necesito que [accion concreta y acotada].

[4. Restricciones]
- Usa [framework/libreria/patron].
- Cumple [reglas de seguridad, rendimiento, estilo o arquitectura].
- Maneja [errores/casos borde].
- No hagas [limites claros].

[5. Formato]
Devuelveme [codigo, checklist, tabla, pasos, diff, etc.] con [nivel de detalle].

Ejemplo del curso

[1. Rol]
Actua como un desarrollador backend Senior especializado en ciberseguridad.

[2. Contexto]
Estoy construyendo una API REST para un e-commerce usando Python 3.14.

[3. Tarea]
Necesito que escribas un endpoint para el login de usuarios.

[4. Restricciones]
El endpoint debe estar hecho con FastAPI. Debe recibir un email y una contrasena,
validar credenciales simulando una consulta a PostgreSQL y devolver un token JWT.
Incluye manejo de errores, por ejemplo 401 si fallan las credenciales, y usa
contrasenas hasheadas con bcrypt.

[5. Formato]
Devuelveme unicamente el bloque de codigo bien comentado, sin explicaciones previas.

Checklist antes de aceptar codigo IA

  • Da contexto y pide seguridad por adelantado.
  • Lee y entiende el codigo completo antes de aprobarlo.
  • Pide explicaciones de lo que no entiendas.
  • Pasa tests, build y revisiones antes de subir cambios.
  • No pegues claves, datos reales de clientes ni secretos en prompts.

2. Agentes, contexto y herramientas

Build vs. Plan

Build Mode: el agente actua directamente sobre el codigo. Util para tareas atomicas, prototipos o bugs evidentes.
Plan Mode: primero propone estrategia y espera revision. Mejor para tareas grandes, refactors y decisiones con riesgo.

AGENTS.md

Archivo de reglas persistentes del proyecto. Debe ser claro, corto y accionable; el curso recomienda no superar unas 500 lineas.

# [Nombre del proyecto]
[Una o dos frases: que es el proyecto y para quien.]

## Stack
- Lenguaje: [p. ej. TypeScript estricto]
- Framework / runtime: [p. ej. Node 22 + Express 5]
- Base de datos: [p. ej. PostgreSQL con Prisma]
- Tests: [p. ej. Vitest]

## Comandos
- `[comando dev]` - arranca el servidor en local
- `[comando test]` - ejecuta los tests antes de cada commit
- `[comando lint]` - revisa el estilo antes de cada PR
- `[comando build]` - compila para produccion

## Estructura del proyecto
- `[carpeta]/` - [que contiene]
- `[carpeta]/` - [que contiene]

## Convenciones
- [Estilo de nombres.]
- [Donde van los tests.]
- [Manejo de errores.]
- [Patron obligatorio, p. ej. validar toda entrada de usuario.]

## No hagas
- [No instalar dependencias sin avisar.]
- [No tocar zonas congeladas.]
- [No subir archivos .env* al repositorio.]
- [No usar `any` sin justificarlo.]

## Flujo de trabajo
- Antes de una tarea no trivial, propon un plan y espera mi OK.
- Una tarea a la vez.
- Al terminar, dime que cambiaste para revisarlo.
- Si no estas seguro al 80%, pregunta. No inventes.

3. Especificaciones, multiagentes y verificacion

Spec-Driven Development (SDD)

Definicion: estrategia para reducir el indeterminismo de la IA usando una especificacion tecnica como contrato y memoria persistente.
Objetivo: pasar de "hazme X" a "implementa esta spec". Reduce perdida de contexto, cambios invisibles, ambiguedad, prueba/error y deuda cognitiva.
Nivel recomendado para empezar: spec-anchored. La spec se mantiene viva y se actualiza antes de cambios importantes.
Paso Funcion
1. ConstitucionReglas generales del proyecto, una vez por proyecto.
2. SpecifyQue se va a construir y criterios de aceptacion.
3. PlanComo se va a construir: enfoque tecnico, archivos y datos.
4. TasksDividir el plan en tareas pequenas y verificables.
5. ImplementEl agente ejecuta las tareas una a una.
6. VerifyValidar contra criterios de aceptacion y ajustar si falla.

Artefactos SDD

mi-proyecto/
|-- spec/
|   |-- constitution/
|   |   |-- mission.md       # que construimos y para quien
|   |   |-- tech-stack.md    # tecnologias y convenciones
|   |   `-- roadmap.md       # orden de features
|   `-- features/
|       |-- 001-tarea/
|       |   |-- spec.md      # que hace y criterios de aceptacion
|       |   |-- plan.md      # como se implementa
|       |   `-- tasks.md     # checklist de tareas
|       `-- 002-tarea/
`-- codigo/                  # codigo generado por el agente

Niveles SDD

  • Spec-first: escribes spec, generas codigo una vez y despues editas codigo directamente.
  • Spec-anchored: la spec se mantiene viva. Cada cambio importante actualiza antes la spec.
  • Spec-as-source: solo editas la spec y regeneras codigo desde ella. Experimental.

Multiagentes y loops

Subagente: agente hijo con su propia ventana de contexto, rol y permisos. Hace una tarea concreta y devuelve solo el resumen util.
Flujo: coordinador divide y asigna, implementador ejecuta, verificador prueba y revisa.
Loop engineering: ciclo actuar → observar → corregir hasta cumplir un criterio. Ejemplo: arreglar tests hasta que todo pase.
